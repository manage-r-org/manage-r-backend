## Phase 2 — Login (complete)

POST /api/v1/auth/login
- `LoginDto` — single `identifier` (username OR email) + strong password.
- `AuthRepository.findByLoginIdentifier` — `findFirst` OR lookup, includes `sec_role`.
- `AuthService.login` — find -> `comparePassword` (bcrypt) -> inactive check -> sign access + refresh JWTs.
- Generic `Invalid credentials.` (401) for both unknown identifier and wrong password (no account enumeration); 403 for disabled accounts.
- Tokens signed with the project's existing claims contract `{ sub, email, roles }`; access token uses module default (access secret/15m), refresh token uses `JWT_REFRESH_SECRET`/`JWT_REFRESH_EXPIRATION` (7d).
- `LoginResponse` mapper — accessToken, refreshToken, tokenType, expiresIn (from decoded `exp`).
- `INVALID_CREDENTIALS` message generalized from "Invalid email or password." to "Invalid credentials.".
- Unit tests: `auth.service.spec.ts` (login block), `login.dto.spec.ts` (26 tests total pass).
- Verified end-to-end: email login 200, username login 200, wrong password 401, unknown identifier 401 (identical body), disabled account 403, weak/missing payload 400, role injection 400. Tokens cross-verified: access only verifies with access secret, refresh only with refresh secret; claims contain no password/hash.

## Phase 3 — Refresh (complete)

POST /api/v1/auth/refresh
- `RefreshTokenDto` — single `refreshToken` field, missing/empty -> 400.
- `AuthController.refresh` — `@Public()` (no access-token guard), route stays inside the auth module.
- `AuthService.refresh` — `verifyRefreshToken` (jwtService.verifyAsync, `JWT_REFRESH_SECRET`) -> `findByIdWithRole(sub)` -> inactive check (403) -> `signAccessToken(buildAuthTokenPayload)` (same call login uses).
- Generic `Invalid or expired refresh token.` (401) for expired, malformed, wrong-secret, access-token, deleted-user; reason logged only (`refresh_token_rejected` + error name).
- Stateless: no refresh-token persistence, no rotation; the client reuses the same refresh token until expiry (7d).
- `RefreshResponse` mapper — accessToken, tokenType, expiresIn (900); no refreshToken echoed, no password/hash.
- Unit tests: `refresh-token.dto.spec.ts`, `auth.service.spec.ts` refresh block (42 total pass).
- Verified end-to-end: valid refresh 200 (no auth header) with fresh access token verified against access secret (claims {sub,email,roles}, 15m), access-token-as-refresh 401, tampered 401, malformed 401, expired 401, nonexistent user 401, disabled account 403, missing/empty 400, privileged-field injection 400. No token/password strings in logs.

## Phase 4 — Logout (complete)

POST /api/v1/auth/logout
- Protected by the global `JwtAuthGuard` (no `@Public()`); identity comes from `@CurrentUser()` → verified access token, never from the body (no DTO, no body).
- `AuthService.logout` — logs `user_logged_out` event with `userId` and returns `{ message: 'Logout successful.', data: null }` (interceptor → `{ success, message, data: null }`). Synchronous, idempotent.
- `LogoutResponse` type added to `auth.mapper.ts`. No repository change.
- Architecture determination: refresh tokens are **stateless** (A) — never persisted, not rotated, no session record. Logout therefore cannot revoke server-side; it is client-side token disposal. Documented limitation: already-issued access/refresh tokens remain valid until natural expiry, and `/auth/refresh` still accepts a pre-logout refresh token. No sessions/blacklist/Redis was invented.
- Unit tests: `auth.service.spec.ts` logout block (46 total pass).
- Verified end-to-end: valid token 200 with `data: null`, repeated 200, body-injected `userId`/`role` ignored (identity from token), missing/garbage/wrong-secret tokens 401, `user_logged_out` logged, zero token/password/body-id strings in logs.

## Phase 5 — Current user (complete)

- `MeResponse` + `toMeResponse` in `auth.mapper.ts` — `{ userId (BIGINT as string), username, email, phoneNumber, role }`; role re-derived from the DB, not trusted from the JWT; password hash, tokens, `is_active`, `role_id` never exposed.
- `findByIdWithRole` already existed (added in Phase 3 for refresh) — no repository change.
- Unit tests: `auth.service.spec.ts` getMe block (6 new tests, 52 total pass).
- Verified end-to-end: valid token 200 with safe payload, spoofing (query/body/header userId) ignored, missing/garbage/refresh-as-access tokens 401, nonexistent user 404, disabled account 403, no sensitive fields in the response.

## Phase 7 — Create profile (complete)

POST /api/v1/profile
- Protected by the global `JwtAuthGuard` (no `@Public()`); ownership comes from `@CurrentUser()` → verified access token, never from the body. The DTO has no `userId`/`profileId`, and the global `ValidationPipe` (whitelist + forbidNonWhitelisted) rejects them with 400 `property userId should not exist`.
- `ProfilesController.createProfile` — thin; passes `@CurrentUser()` + validated `CreateProfileDto` to the service. `@ApiStandardResponse(HttpStatus.CREATED, ...)`.
- `CreateProfileDto` (`profiles/dto/create-profile.dto.ts`) — all 13 profile fields optional (schema allows null everywhere), class-validator rules matching DB column lengths (`@IsString`, `@MaxLength`, `@IsEmail`, `@IsDateString`), `ApiPropertyOptional` docs.
- `ProfilesService.createProfile` — 409 `ALREADY_EXISTS('Profile')` if `findByUserId` already finds one (CREATE, never overwrites), then `createProfile(user.id, dto)`, then P2002 unique-constraint catch → same 409 (race-condition safety net, like `AuthService.register`). Logs `profile_created`. Logger added to `ProfilesService` (was absent for the pure-read GET).
- `ProfilesRepository.createProfile` — maps DTO → snake_case Prisma data; `user_id: BigInt(userId)` from the JWT identity only; `dob` converted string→`Date` (Prisma's DateTime parser rejects a bare `"1995-01-01"`).
- Response uses the existing `ProfileResponse` + `toProfileResponse` (no new mapper).
- Unit tests: `profiles.service.spec.ts` createProfile block (6 new tests, 62 total pass).
- Verified end-to-end: 201 with full body (dob round-trips to `1995-01-01`), DB row `user_id` = authenticated user (ownership), duplicate 409, missing/garbage tokens 401, `userId` injection 400, invalid email 400, invalid dob 400, GET after POST 200, zero 500s.

## Phase 8 — Update profile (complete)

PATCH /api/v1/profile
- Protected by the global `JwtAuthGuard` (no `@Public()`); ownership is inherent — the profile updated is always the authenticated user's own (`@CurrentUser()` → `user.id`), and the DTO has no `userId`/`profileId`, so the ValidationPipe (whitelist + forbidNonWhitelisted) rejects any attempt to target another row (400 `property userId should not exist`).
- `ProfilesController.updateProfile` — thin; `@Patch()` on the `profile` route. `@ApiStandardResponse(HttpStatus.OK, SUCCESS_MESSAGES.UPDATED('Profile'))`.
- `UpdateProfileDto` (`profiles/dto/update-profile.dto.ts`) — `extends CreateProfileDto`, so the same 13 optional fields/rules apply; PATCH semantics: only the supplied fields change.
- `ProfilesService.updateProfile` — `isDtoEmpty` (all values `undefined`) → 400 `NOTHING_TO_UPDATE` (a body of `{}` is rejected before any DB call); `findByUserId` → 404 `NOT_FOUND('Profile')` if the account has no profile (PATCH never creates one); `updateByUserId`; P2025 catch → 404 (race safety net). Logs `profile_updated`. Note: an explicit `null` is treated as clear-the-field intent (not an empty body) — supported because the schema columns are nullable.
- `ProfilesRepository.updateByUserId` — `update({ where: { user_id: BigInt(userId) }, data: {...} })`; same DTO→snake_case mapping as create, including the `dob` string→`Date` conversion; a field left `undefined` is ignored by Prisma (never overwritten).
- Schema fix (data integrity): added `@updatedAt` to `profile.updated_at` in `prisma/schema.prisma` — Prisma now sets it on create and update (previously stayed `null` forever, yet was exposed as `updatedAt` in responses). Applied via `prisma db push` (repo uses db push, no migrations dir; `prisma migrate dev` was NOT used — it would have demanded a destructive reset).
- Unit tests: `profiles.service.spec.ts` updateProfile block (8 new tests, 70 total pass).
- Verified end-to-end: partial single-field update 200 (other fields preserved), multi-field update 200, subsequent single-field PATCH preserves earlier fields, missing/garbage/refresh-as-access tokens 401, empty body `{}` 400 `Nothing to update.`, invalid email 400, `userId` injection 400, user B's PATCH never touches user A's row (ownership), account without a profile row 404, `updatedAt` now populated in response + DB after PATCH, zero 500s.

## Phase 9 — Delete profile (complete)

DELETE /api/v1/profile
- Protected by the global `JwtAuthGuard` (no `@Public()`); the profile is resolved from `@CurrentUser()` → `user.id`, never from the request. There is no route like `DELETE /api/v1/profile/:id` and no body/query/header identifier is accepted — a client can only ever delete its own profile (no IDOR).
- `ProfilesController.deleteProfile` — thin; `@Delete()` on the `profile` route. `@ApiStandardResponse(HttpStatus.OK, SUCCESS_MESSAGES.DELETED('Profile'))`.
- `ProfilesService.deleteProfile` — `findByUserId(user.id)` → 404 `NOT_FOUND('Profile')` if the account has no profile (DELETE never creates one) → `deleteByUserId(user.id)` → logs `profile_deleted` → returns `{ message: SUCCESS_MESSAGES.DELETED('Profile'), data: null }`. P2025 catch → 404 (race safety net, same as PATCH). The deleted row is never returned.
- `ProfilesRepository.deleteByUserId` — `delete({ where: { user_id: BigInt(userId) } })`; `user_id` is `@unique`, so at most one row per account.
- `DeleteProfileResponse` in `profiles/mappers/profile.mapper.ts` — `{ message, data: null }`, the same convention as auth logout; the interceptor wraps it into `{ success, message, data: null }`.
- Deletion semantics are unchanged from the existing database design — verified all FKs referencing `profile` are `ON DELETE CASCADE` in the live DB (`certification`, `education`, `experience`, `job_application`, `profile_skill`, `project`, `resume`); `sec_user` is untouched. No schema change, no migration, no new cascade rules.
- Unit tests: `profiles.service.spec.ts` deleteProfile block (6 new tests, 76 total pass).
- Verified end-to-end: no token / garbage token 401, DELETE (with `userId`/`profileId` smuggled in body/query/header) 200 + DB row gone + education/project child rows cascaded + `sec_user` intact, repeat DELETE 404, ownership (user C's DELETE with user D's id in body deleted only C's own profile; D's profile untouched).

## Phase 10 — Education CRUD (complete)

GET/POST /api/v1/profile/education, PATCH/DELETE /api/v1/profile/education/:educationId
- Routes are nested under the profile resource (`@Controller('profile/education')`) — education hangs off a profile, which hangs off exactly one `sec_user`. This replaces the placeholder `@Controller('education')` and becomes the documented contract.
- Protected by the global `JwtAuthGuard` (no `@Public()`); ownership comes from `@CurrentUser()` → verified access token, never from the body (DTOs have no `profileId`/`educationId`/`userId`; the ValidationPipe rejects them with 400 `property profileId should not exist`). A foreign `:educationId` matches nothing → 404 (no IDOR).
- `ParseBigIntPipe` (new, `src/common/pipes/parse-bigint.pipe.ts`) validates `:educationId` on PATCH/DELETE — BIGINT ids exceed JS safe-integer range so the value stays a string; anything not matching `/^\d{1,19}$/` → 400 `"abc" is not a valid id.` (mirrors the existing `ParseUuidPipe`).
- `CreateEducationDto` (`education/dto/create-education.dto.ts`) — all 8 education fields optional (schema allows null everywhere), class-validator rules matching DB column lengths (`@IsString`, `@MaxLength` for degree 200 / institution 255 / fieldOfStudy 255 / grade 50, `@IsDateString` for startDate/endDate, `@IsBoolean` for isCurrent, `@IsString` for description). `UpdateEducationDto extends PartialType(CreateEducationDto)` for PATCH semantics.
- `EducationResponse` + `toEducationResponse` in `education/mappers/education.mapper.ts` — whitelist of the entry's own fields; `educationId`/`profileId` as strings (BIGINT); no sec_user internals. `DeleteEducationResponse` = `{ message, data: null }` (same convention as profile delete / auth logout).
- `EducationRepository` (extends `BaseRepository<education>`) — every method scopes by `profile.user_id` (the profile's owner), so the DB itself enforces ownership even with a foreign id:
  - `findProfileIdByUserId` — resolves the profile id from the JWT identity; `null` when the account has no profile.
  - `findAllByUserId` — list, ordered `start_date desc, nulls last`, then `education_id desc`.
  - `findOwnedById` — single owned row (used to re-fetch after an updateMany, which returns no row).
  - `createEducation(profileId, dto)` — `profile_id` from the JWT identity only; start/end dates string→`Date` (Prisma rejects a bare `"2020-01-15"`).
  - `updateOwnedEducation` / `deleteOwnedEducation` — `updateMany`/`deleteMany` scoped by `user_id` + `education_id`; return affected counts (never throw), service turns `0` into 404. No P2025 handling needed.
- `EducationService` — thin flows: list (empty `[]` when no profile/entries); create (404 `Profile not found.` without a profile, P2003 FK race → same 404); update (empty body → 400 `Nothing to update.`, count 0 → 404 `Education not found.`); delete (count 0 → 404, success-only response). Logs `education_created`/`education_updated`/`education_deleted`. Logger added to `EducationService` (was absent for the placeholder).
- `EducationController` — `@Get()` list, `@Post()` create, `@Patch(':educationId')`, `@Delete(':educationId')` with `ParseBigIntPipe`. All `@ApiStandardResponse`-documented.
- Unit tests: `education.service.spec.ts` (22 new tests, 98 total pass).
- Verified end-to-end: list-without-profile `[]`, create-without-profile 404, full-body create 201 (dates round-trip to `1995-01-01` style), list 200, partial PATCH 200 (other fields preserved), empty body 400, invalid `:educationId` 400, `profileId`/`userId` injection 400, no/garbage token 401, cross-user PATCH/DELETE 404 (IDOR-proof — target row untouched), ordering (start_date desc, nulls last), own DELETE 200 + repeat DELETE 404, zero 500s.

## Phase 11 — Experience CRUD (complete)

GET/POST /api/v1/profile/experience, GET/PATCH/DELETE /api/v1/profile/experience/:experienceId
- Routes are nested under the profile resource (`@Controller('profile/experience')`) — experience hangs off a profile, which hangs off exactly one `sec_user`. This replaces the placeholder `@Controller('experience')` and becomes the documented contract. Same pattern as Education (Phase 10), extended with the GET-one flow.
- Protected by the global `JwtAuthGuard` (no `@Public()`); ownership comes from `@CurrentUser()` → verified access token, never from the body (DTOs have no `profileId`/`experienceId`/`userId`; the ValidationPipe rejects them with 400 `property profileId should not exist`). A foreign `:experienceId` matches nothing → 404 (no IDOR, no existence leak — GET/PATCH/DELETE all return 404, never 403).
- `ParseBigIntPipe` (already added in Phase 10, reused — no new pipe) validates `:experienceId` on GET/PATCH/DELETE — anything not matching `/^\d{1,19}$/` → 400 `"abc" is not a valid id.` (verified for `abc`, `12abc`, `1.5`, `-1`).
- `CreateExperienceDto` (`experience/dto/create-experience.dto.ts`) — all 8 experience fields optional (schema allows null everywhere; `experience` has no `created_at`/`updated_at` columns), class-validator rules matching DB column lengths (`@IsString`, `@MaxLength` for companyName 255 / position 255 / employmentType 100 / location 255, `@IsDateString` for startDate/endDate, `@IsBoolean` for isCurrent, `@IsString` for description). `UpdateExperienceDto extends PartialType(CreateExperienceDto)` for PATCH semantics.
- `ExperienceResponse` + `toExperienceResponse` in `experience/mappers/experience.mapper.ts` — whitelist of the entry's own fields; `experienceId`/`profileId` as strings (BIGINT); no sec_user internals; no timestamps (the table has none). `DeleteExperienceResponse` = `{ message, data: null }`.
- `ExperienceRepository` (extends `BaseRepository<experience>`) — mirrors `EducationRepository`; every method scopes by `profile.user_id`:
  - `findProfileIdByUserId` — resolves the profile id from the JWT identity; `null` when the account has no profile.
  - `findAllByUserId` — list, ordered `start_date desc, nulls last`, then `experience_id desc`.
  - `findOwnedById` — single owned row (GET-one flow + re-fetch after an updateMany).
  - `createExperience(profileId, dto)` — `profile_id` from the JWT identity only; start/end dates string→`Date` (Prisma rejects a bare `"2019-05-01"`).
  - `updateOwnedExperience` / `deleteOwnedExperience` — `updateMany`/`deleteMany` scoped by `user_id` + `experience_id`; return affected counts (never throw), service turns `0` into 404. No P2025 handling needed.
- `ExperienceService` — thin flows: list (empty `[]` when no profile/entries); get one (ownership-scoped query → 404 `Experience not found.`); create (404 `Profile not found.` without a profile, P2003 FK race → same 404); update (empty body → 400 `Nothing to update.`, count 0 → 404); delete (count 0 → 404, success-only response). Logs `experience_created`/`experience_updated`/`experience_deleted`. Logger added to `ExperienceService` (was absent for the placeholder).
- `ExperienceController` — `@Get()` list, `@Post()` create, `@Get(':experienceId')`, `@Patch(':experienceId')`, `@Delete(':experienceId')` with `ParseBigIntPipe`. All `@ApiStandardResponse`-documented.
- **Responsibilities decision:** `experience_responsibility` is NOT exposed in this phase's contract — no create/update/read of responsibilities, no separate endpoints (they have their own composite PK `(experience_id, display_order)` and ordered-array semantics; a future phase handles them). Deleting an experience cascades its responsibility rows automatically at the database level (FK `ON DELETE CASCADE`, verified live), so no orphan handling is needed.
- Unit tests: `experience.service.spec.ts` (29 new tests — includes a dedicated `security / cross-user isolation` block proving B cannot GET/PATCH/DELETE A's row and A's row stays unchanged; 127 total pass).
- Verified end-to-end: full-body create 201 (dates round-trip), list 200, GET one 200, partial PATCH 200 (only supplied fields changed, DB-confirmed), empty body 400, malformed ids 400 (`abc`/`12abc`/`1.5`/`-1`), no/garbage token 401, `profileId`/`userId`/`experienceId` injection 400, oversized companyName 400, invalid date 400, no-profile create 404 + list `[]`, cross-user GET/PATCH/DELETE 404 (B's attempts never touched A's row), ordering (start_date desc, nulls last), own DELETE 200 + repeat DELETE 404, responsibility cascade on delete (DB-confirmed), zero 500s. (Note: a string like `"yes"` for `isCurrent` is coerced to `true` by the global ValidationPipe's `enableImplicitConversion` — identical to Education, pre-existing global behavior.)
